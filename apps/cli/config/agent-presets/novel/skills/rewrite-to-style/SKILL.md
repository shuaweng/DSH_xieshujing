# Rewrite To Style

这不是“随便润色一下”。

它是一个**窄权限改写 skill**：

- 保留核心剧情与事实
- 不乱扩设定
- 不偷偷改结构问题
- 只改表达、节奏、对白、信息露出方式和整体气质

## 核心目标

重点处理 5 类任务：

1. 去 AI 味
2. 调句法节奏
3. 拉开对白声音
4. 收修信息露出方式
5. 把文本拉向明确风格目标

## 何时使用

优先在这些场景使用：

- “把这段改得更像网文”
- “少解释一点，重写这段”
- “把这章收紧，但别大改剧情”
- “按这个风格改一下表达”
- “对白太像一个人说的，帮我改”
- “先按审稿意见重写，不要再分析一遍”

## 不要做的事

- 不要擅自新增重大设定、人物动机或世界规则。
- 不要把 candidate 写成 confirmed。
- 不要把结构问题伪装成措辞问题去硬修。
- 不要在用户只要局部改写时误伤整章结构。
- 不要把“更有风格”写成“更花哨”。

## 先读哪些参考

按需读取：

- `references/rewrite-style-checklist.md`
  - 默认主参考
- 如果用户已先做审稿：
  - 先吸收 `style-audit` / `info-release-check` 的问题单

  - 转 `chapter-execution`

## 工作流

### 步骤 0：先判断改写范围

先判断这次是：

- 句子级
- 段落级
- 局部片段级
- 整章级

如果用户没有明确范围，不要默认重写整章。

### 步骤 1：先锁定“不能改什么”

至少先确认：

1. 哪些事实不能改
2. 哪些人物关系不能改
3. 哪些信息不能提前说破
4. 哪些情节节点必须保留

如果这些边界不清，先保守处理。

### 步骤 2：锁定目标风格

风格来源按这个顺序找：

1. 用户本轮明确要求
2. `STYLE.md`
3. 已有正文的有效语感
4. `style-audit` / `info-release-check` 给出的修改方向

常见目标包括：

- 更像连载网文
- 更冷
- 更收
- 更顺
- 更少解释
- 更有对白辨识度
- 更自然地带出钩子
- 更快亮出卖点
- 更有主角嘴脸
- 从影视感改成网文感

### 步骤 3：先决定这次主要改哪一层

不要每次都全改。

优先判定这次主要是：

- `AI 味 / 套路表达`
- `句法节奏`
- `对白声音`
- `信息露出方式`
- `章末收口`
- `网文味 / 卖点前置 / 主角嘴脸`

一轮改写最好只主攻 1 到 2 层，避免失控。

### 步骤 4：按层改写

#### A. AI 味 / 套路表达

重点处理：

- 三段式凑数
- 过度平滑
- 抽象泛化
- 宣传式描写
- 通用积极结尾

> **去 AI 味时的三个修订方向**（先用 `style-audit` 的四类病定位，再按对应方向改）：
>
> 1. **具体动作**替抽象状态：把"他感到一阵难受"改成一个可见动作（"他把没点的烟摁灭在桌面上"）。
> 2. **更锋利节奏**替平滑流畅：删过渡词，让句子硬碰硬，长短错落，砍掉重复盖章只留最有画面的一句。
> 3. **人物专属感知**替通用镜头：同一场景，换成这个角色独有的注意力（猎人看逃生路线，厨子看火候），而不是作者的全知旁白。
>
> 四类病→方向对应：抽象情绪标签②/低具体度描写④ → 方向1+3；重复措辞①/过整齐过渡③ → 方向2。
> 铁律：**只去味，剧情事件和连续性不变。**

#### B. 句法节奏

重点处理：

- 长句过多
- 段落发闷
- 关键句力点埋掉
- 轻重句型没有层次

#### C. 网文味 / 卖点前置 / 主角嘴脸

重点处理：

- 开篇氛围镜头过多，核心机制和具体死局出现太晚
- 主角太像冷静求生者，缺少贱、狂、损、冷幽默、疯批、狠劲或强欲望
- 设定讲得完整，但没有转化成“他怎么赢、怎么搞事、怎么让对方误判”
- 只有 promise 没有第一层 payoff

改写时可以把同一段从“影视分镜”改成“网文钩子”：

- 先抛 `好消息/坏消息/离谱限制/倒计时/赌注`
- 再让主角用一句判断、吐槽、挑衅或算盘立住
- 设定只保留马上会被主角利用的部分
- 让段落落在机会、误判、挑衅、上桌、反杀入口上

#### D. 对白声音

重点处理：

- 角色口气同质化
- 台词过于完整、过于“正确”
- 缺潜台词
- 对话承担解释任务

#### E. 信息露出方式

重点处理：

- 先给效果，再慢慢给原理
- 让动作、反应、后果带信息
- 删“正确但没必要”的解释
- 不让配角太早替读者总结

#### F. 章末收口

重点处理：

- 删作者腔悬念句
- 把最后一句落在变化、风险、决定或未落地结果上
- 不把翻页理由埋在解释堆后面

### 步骤 5：改完后做最小自检

至少确认：

1. 事实是否没变
2. 设定是否没乱扩
3. 信息是否没被提前说破
4. 文气是否更接近目标，而不是更花
5. 如果是整章，章末是否没被写软

## 默认输出方式

- 直接改目标文件
- 聊天里只简短说明：
  - 这次主要改了哪一层
  - 有没有刻意保留的边界

### 如果用户给的是聊天片段

```md

- ...

## 改写版本
...

## 这次主要调整

2. ...
3. ...
```

## 判断边界

### 什么时候不要用本 skill

- 主要问题是卷目标、章目标或 beat 没立住
- 主要问题是冲突太弱、推进链发虚
- 用户其实要的是续写，不是改写

这时应分别转给：

- `outline-beat-design`
- `scene-drive`
- `chapter-execution`

### 什么时候一定要保守改

- 用户没给明确风格目标
- 片段涉及 confirmed 真源
- 当前段落承接大量后续 canon
- 你怀疑一处句子背后其实是结构问题

## 和其他 skill 的关系

- 风格 / AI 味 / 对白审稿：`style-audit`
- 对话层专项诊断（声音区分、潜台词、信息倾泻、网文对话模式）：`dialogue-diagnostics`
- 信息释放审稿：`info-release-check`
- 单章推进链设计：`scene-drive`
- 卷纲 / 分章 / beat 规划：`outline-beat-design`
- 完整正文执行：`chapter-execution`

默认关系是：

- `style-audit` / `info-release-check` 负责指出该怎么改
- `rewrite-to-style` 负责受控改写表达层
- `scene-drive` 负责结构层修法
- `chapter-execution` 负责更完整的正文任务
- `skill-evolution` 负责记录反馈、沉淀偏好

> 💡 如果用户回退了部分改动或表达了风格偏好，可以提示：
> "要不要让 skill-evolution 记录一下这次的反馈？"
