# Chapter Execution

把“项目资产”真正转成“可用正文”。

## 核心目标

基于：

- `PROJECT.md`
- `STYLE.md`
- `confirmed` 真源
- 当前卷纲 / 章纲
- 当前章节文件
- 章节索引 / 章节摘要 / 上一章正文 / 必要账本

来完成这些动作之一：

- 续写一章
- 改写一章
- 收紧一章
- 重写某段或某章

同时守住这五条底线：

1. 不乱扩设定
2. 不把 candidate 当 confirmed
3. 不把解释写成故事
4. 不把网文开场写成严肃影视分镜或设定说明片
5. 不把全部旧正文无脑塞进上下文

## 何时使用

优先在这些场景使用：

- “继续写第 X 章”
- “把这一章重写一下”
- “按卷纲把这一章推进下去”
- “把这章收紧一点”
- “根据设定和前文，直接落稿”

## 不要做的事

- 不要在缺少最小项目资产时直接裸写正文。
- 不要忽略 `PROJECT.md / STYLE.md`。
- 不要擅自引入重大新设定、新规则、新人物动机。
- 不要在应该落稿时只回一堆建议。
- 不要在只需要短试写时误改整份项目文件。
- 不要为了写新章默认读取全部历史章节正文。
- 不要把章节摘要、章节索引当成未来大纲；它们只记录已写正文事实。

## 输入优先级

正文执行时，按这个顺序找依据：

1. 当前轮用户明确要求
2. `PROJECT.md`
3. `STYLE.md`
4. `confirmed` 真源文件
5. 当前 `working` 卷纲 / 章纲
6. `资料/章节索引.md`、近期章节摘要、上一章正文、当前章节文件
7. `candidate` / `open` 只作参考，不能直接当正式事实

## 工作流

### 步骤 0：判断任务类型

先判断当前任务是：

- `continue`
- `rewrite`
- `tighten`
- `partial rewrite`

并判断产物该去哪里：

- 如果目标文件明确且是项目正文，优先改文件
- 如果只是试写、示例段落、风格试验，优先回聊天

### 步骤 1：检查最小上下文是否齐

默认至少检查：

- `PROJECT.md`
- `STYLE.md`（如有）
- 当前章节文件
- 与本章直接相关的设定
- 当前卷纲 / 本章计划
- `资料/章节索引.md` 或等价章节索引
- `资料/事实账本.md`、`资料/伏笔账本.md`、`资料/连续性账本.md` 中与本章相关的内容
- 如果在写前 3 章，优先检查 `大纲/前三章作战图.md`

如果用户要求续写，还应尽量读：

- 上一章
- 当前章已有内容

如果用户要写的是新章节，还应尽量读：

- 上一章正文全文
- 最近 2-3 章的章节摘要
- `资料/章节索引.md` 中所有已写章节的短索引
- `资料/连续性账本.md` 中的上一章章末动作、当前地点、主角状态和必须承接危机

默认不要读：

- 全部旧正文
- 全部旧章节摘要全文
- 与当前章无关的历史资料

只有在这些情况下，才允许定点读取更早旧章全文：

- 章节索引显示本章正在回收某个旧伏笔
- 本章涉及旧人物、旧道具、旧地点的精确连续性
- 最近摘要不足以判断事实边界
- 用户明确要求对照某一章

读取旧章全文时，必须先说明读取理由，并只读相关章节，不要顺手扫全书。

卷纲要求：

- 写前 3 章：必须优先读取 `大纲/前三章作战图.md` 或等价黄金三章规划。
- 写第 4 章及以后：必须优先读取当前卷 `大纲/卷纲.md` 或等价卷纲文件。
- 如果缺当前卷纲，不要直接长篇续写；先接 `outline-beat-design` 补出当前卷目标、未来 3-5 章职责、爽点节奏和章末入口。
- 如果只有设定集，没有卷目标、阻力、兑现、卷末变化和章节职责，也视为卷纲不足。

如果这些严重缺失：

- 先提示缺什么
- 不要强行硬写整章

章节资产要求：

- 如果项目已经有正文但缺 `资料/章节索引.md` 或 `资料/章节摘要/`，写新章前应先提示补建。
- 如果用户要求继续写且不想停，至少先临时从上一章正文抽一版“上一章承接摘要”，再开始写。
- 如果连续写多章，必须在每章结束后同步章节摘要和章节索引，否则下一章上下文会退化成全量回读。

### 步骤 2：执行前校准

在真正写之前，先明确这 5 件事：

1. **本章推进目标**
   - 这章到底要把什么往前推

2. **本章不能碰的东西**
   - 哪些正式设定不能改
   - 哪些剧情节点必须保留

3. **信息释放边界**
   - 哪些可以说
   - 哪些不能提前说破

4. **风格约束**
   - 本项目要的气质是什么
   - 禁止的 AI 味是什么

5. **章末落点**
   - 这章最后应该停在什么情绪、风险、钩子上

再额外做一次**网文味校准**，尤其是脑洞文、废土文、无限流、修仙脑洞文、都市脑洞文：

6. **本章卖点一句话**
   - 这一章让读者继续看的核心卖点是什么
   - 如果是前 3 章，前 300 字内必须让读者知道“这本书凭什么不一样”

7. **主角可识别嘴脸**
   - 主角这章是贱、狂、损、冷幽默、疯批、克制狠人，还是别的明确味道
   - 不要只写“冷静、理性、求生”，那会像影视硬汉，不像连载网文男主

8. **爽点兑现方式**
   - 这章的 promise 是什么
   - 这章至少兑现哪一层：小胜、打脸、规则漏洞、资源到手、身份变化、敌人误判、观众震惊
   - 如果只能写“继续铺垫”，先回到 `outline-beat-design` 重排

9. **上下文预算与读取边界**
   - 本章使用哪些资产作为依据
   - 哪些旧章节只看摘要
   - 哪些旧章节需要全文读取，理由是什么
   - 如果没有明确理由，不允许扩读历史正文

### 步骤 2.5：新章节重复疲劳校验

如果当前任务是在写**新章节**，尤其是前 5 章内的新章，先检查近 3 章是否在重复刷同一模板：

1. **主冲突类型是否重复**
   - 连续两章是不是都在同一种威胁结构里打转

2. **主 arena 是否重复**
   - 冲突是不是总发生在同一个场景容器里，只是换人或加码

3. **主解法是否重复**
   - 主角是不是又靠同一招过关

4. **局面变化是否重复**
   - 结果是不是只是“赢一次、涨一点、再被更狠的人盯上”

5. **章末钩子类型是否重复**
   - 是否连续两章都靠抽象悬念、作者腔预告或同类揭示收口

6. **压迫-逃生-再压迫是否重复**
   - 是否连续多章都在“遇险、硬逃、再规划奖励/下一步”之间原地循环
   - 如果是，必须换成信息差、资源兑现、关系变化、规则反杀、地位变化等不同推进类型

7. **主角状态是否只变数值不变处境**
   - 如果本章结束主角只获得一点资源/经验，但关系、地位、目标、敌人判断都没变，说明推进不够

如果出现以下任一情况，先不要直接落稿，按下表先接对应 skill 再回来执行正文：

- 近两章里有 2 项以上重复
- 第 2 章和第 3 章只是同一模板加码
- 章节目标不清，只能继续沿用上一章的冲突语法

| 当前最缺的是…… | 症状 | 先接 |
|---|---|---|
| 规划层（章职责/分工/beat） | 卷目标或章目标不清；当前任务其实是在定"接下来怎么推"；第 4 章后仍无当前卷纲或卷纲只是设定堆砌 | `outline-beat-design` |
| 单章推进力 | 这章有事但推进链发虚；冲突不够顶、结果打不开下一步；章末只能靠作者腔硬抬 | `scene-drive` |
| 信息释放边界 | 主要问题是解释超额；新设定/底牌/判断讲穿太早；对话在补课不在推进 | `info-release-check` |
| 节奏 | 章末落点和重复节拍发虚 | `pacing-audit` |
| 文气而非剧情 | 核心剧情不用重搭，主要是修文气/节奏/对白/信息露出，更像"按风格目标重写" | `rewrite-to-style` |

### 步骤 3：执行正文

写作时优先遵守：

- 先让事情发生，再解释
- 先给效果，再慢慢给原理
- 让动作、反应、结果带信息
- 优先推进，不原地讲设定
- 卖点优先于氛围，主角动作优先于世界观镜头
- 设定解释只保留“本场景马上能用来翻盘/装逼/加压”的部分

#### 网文味落稿规则

当题材是脑洞爽文或强设定文，默认不要从大片式环境描写开局。更优先使用：

- `好消息 / 坏消息 / 离谱限制`：先把核心机制和反差讲清
- `当前死局 / 倒计时 / 赌注`：立刻给具体危机
- `主角嘴脸 / 吐槽 / 反常识判断`：让读者先喜欢或记住主角
- `规则漏洞 / 机会窗口`：让读者知道主角马上要搞事

**冲突与字数厚度校准（evolved: 2026-05-10）**：
- **字数厚度**：单章尽量向 3000 字靠拢。拒绝干瘪的流水账，通过增加动作博弈、感官细节、心理对赌和环境互动来压实内容。
- **冲突结构**：每一章必须具备完整的“铺垫-情绪-爆发”冲突弧线。
- **前后对比**：通过“前期被轻视/压制 vs 后期反杀/震撼立威”的认知反差来制造爽感。
- **情感锚点**：在冷酷的黑道逻辑中，必须植入能触动读者的人性锚点（如对杜枝这种底层挣扎的复杂共鸣）。

**视角与AI味红线（evolved: 2026-05-11）**：
- **死守主角近景限知视角**：在同一个场景内，严禁开启上帝视角直接描写敌人的内心恐惧或震惊（如“他们感到极度恐惧”、“他无法理解这种手段”）。对手的情绪只能通过主角观察到的**客观物理反应**来传达（例如：发抖、瞳孔涣散、失禁、倒抽凉气、仓皇逃窜）。
- **根除“没有”排比句**：严禁用连续的“没有XXX。没有XXX。没有XXX”来强行烘托冷酷感或气场。这是严重的 AI 味通病。请用正面、具象、动态的动作直接推进画面。

避免把前 800 字主要花在：

- 天色、废墟、气味、广告牌、阵营服饰等氛围镜头
- 主角接收记忆的设定清单
- 对禁忌物、体系、历史灾变的完整说明
- 冷静观察但迟迟没有主动勾局

如果必须写氛围，必须让它服务于可用信息：危险、赌注、机会、敌人误判、主角可利用的规则。

#### 主角出手感

网文主角不是只“处理危机”，而是要让读者感觉他在**夺局**：

- 被动醒来后，尽快给一个主动判断或主动挑衅
- 受压时可以惨，但不能一直憋；要有内心算盘、口头反击或规则操作
- 解释主角能力时，优先写“这个能力怎么让他赢”，不要只写“能力是什么”
- 章末最好停在“他要上桌 / 他已经开始反杀 / 对面被迫按他的规则走”，而不是只停在“危机更大”

#### `continue`

- 保持当前章语气和上下文
- 把局面往卷纲要求的方向推进
- 不要突然切模式

#### `rewrite`

- 保留核心剧情与事实
- 按用户目标重写表达、节奏、气质
- 不擅自扩大剧情范围

#### `tighten`

- 删解释
- 删空转
- 删重复情绪
- 保留信息与推进

#### `partial rewrite`

- 只改指定片段
- 不误伤相邻结构

### 步骤 3.5：写后章节资产同步

如果这次产物是项目正式正文，而不是聊天里的试写片段，写完后必须立即接 `chapter-wrap-sync` 思路做最小同步。

必须更新或创建：

- 当前章对应的 `资料/章节摘要/第XXX章.md`
- `资料/章节索引.md` 中当前章条目
- `资料/连续性账本.md` 中的当前时间线、地点、主角状态、上一章章末动作

按需更新：

- `资料/事实账本.md`
- `资料/伏笔账本.md`
- 人物设定
- 世界规则
- 当前卷纲 / 章纲
- `大纲/未决问题.md`

同步原则：

- 只同步正文已经落地的信息。
- 不把临时灵感写成 confirmed。
- 不把聊天里的未来计划写进章节摘要，除非已经写入正文。
- 摘要要服务下一章写作，重点写“推进、状态、伏笔、承接”，不要复述全文。

### 步骤 4：最小自检

正文完成后，至少自查这 10 件事：

1. 是否符合 `PROJECT.md`
2. 是否符合 `STYLE.md`
3. 是否碰坏 confirmed 设定
4. 是否把 candidate 写成 confirmed
5. 是否有明显 AI 味
6. 是否出现“X个字 / 这八个字 / 四个小字”等精确字数判断。<!-- evolved: 2026-04-25, 基于反馈 #2 -->
   - AI 容易数错，改稿后也容易遗留不准痕迹。
   - 牌匾、资料、纸面短语、笔记标签等场景，优先写“几个字 / 那几个字 / 一行字 / 那行说明”等模糊表述。
   - 除非数字本身是剧情信息，否则不要在正文里精确判断文字数量。
7. 章末是否落在预期钩子或推进点上
8. 是否更新了章节摘要
9. 是否更新了章节索引
10. 是否更新了连续性账本，避免下一章断气

如果是前 3 章，再加查：

11. 前 300 字是否亮出本书差异点或当前死局
12. 主角是否有一句或一个动作能立住“嘴脸”
13. 本章是否有第一层 payoff，而不只是 promise
14. 读完是否明确知道“下一章主角要怎么搞事”

如果发现明显问题，先修掉再交付。

### 步骤 5：决定交付方式

- 如果这是项目正文任务：
  - 直接写入目标文件
  - 聊天里简短汇报改了什么
  - 不重复贴整章全文

- 如果这是试写/示例任务：
  - 直接回聊天
  - 不乱建文件

### 步骤 6：提示后续同步

如果正文带来了新正式信息、卷纲偏移、未决问题变化，应执行或提示：

- 建议接着运行 `chapter-wrap-sync`

如果已经在步骤 3.5 完成同步，则只需简短说明：

- 正文已写入哪个文件
- 章节摘要和章节索引已同步
- 事实 / 伏笔 / 连续性账本是否有更新

## 判断边界

### 什么时候不该继续写

- 项目真源严重缺失
- 当前章节目标完全不清
- 用户要求和 confirmed 真源明显冲突，但没授权改设定

这时应先指出缺口，而不是瞎补。

### 什么时候不要擅自解释

- 新机制第一次出现
- 主角优势还不该被看穿
- 本章爽点依赖“别人不懂、读者先感受到后再慢慢理解”

### 什么时候不要扩设定

- 用户只让你续写/改写
- 当前任务没有授权“可合理补完”
- 你加的新信息会影响后续 canon

## 输出风格要求

正文执行时优先保证：

1. 叙述顺滑度
2. 网文感
3. 钩子力度
4. 卖点显形速度
5. 主角可识别度

避免：

- 开篇像电影镜头，漂亮但卖点迟迟不出现
- 主角只有冷静求生，没有嘴脸、欲望、算盘或反击姿态
- 设定完整但爽点没转化
- 破折号硬强调
- 作者腔宣布大事
- 解释感过重
- 配角过早替读者讲透主角路线
- “X个字 / 这八个字 / 四个小字”等容易数错或改稿后失准的精确字数判断
- 新章节和近 3 章冲突语法、解法、钩子高度同构
