# 改稿信号蒸馏 Skill

从 `.lingtai/revisions/` 中的用户修改与 agent 修订记录里，提炼用户的**文风偏好**和**剧情节奏编排偏好**，产出 `资料/风格指纹卡.md` 的 candidate 修正案。

## 核心理念

- 用户手动改稿是强信号：那是用户亲自动手改出来的偏好。
- 用户让 AI 改稿并认可、没有回退，也是有效信号：说明用户认可这次 agent 的修改方向。
- 用户把 agent 改过的地方又改掉，是更强信号：以用户最终版本为准。
- 本 skill 只产出**候选规则**，不自动写入正式偏好卡；用户拍板后才更新。

## 数据来源

1. `.lingtai/revisions/第NNN章.jsonl`（主数据源）
   - `source: "user"`：用户在两轮对话之间手动修改的 diff。
   - `source: "agent"`：agent 写稿/改稿的 diff。
   - 每条记录是 JSONL 一行，字段为 `time / chapter / source / tool? / kind / diff? / files?`。
2. `.lingtai/diff-cache/第NNN章.json`（旧数据源，兼容用）
   - 迁移前留下的 agent 编辑记录；没有 `source` 字段时按 `source: "agent"` 处理。
3. 当前对话历史
   - 用户让 AI 改稿的 prompt、用户认可/回退的发言，是解释 diff 意图的关键上下文。分析时优先结合当前会话中仍可见的相关用户消息。

## 何时使用

- 用户说“总结一下我的写作偏好 / 风格偏好 / 改稿规律”。
- `.lingtai/revisions/` 已积累 ≥3 章记录，chapter-wrap-sync 或其他 skill 提示可以蒸馏。
- 用户明确表示“以后照我改的这样写”。

## 不要做的事

- 不要在用户未确认前直接写入 `资料/风格指纹卡.md`。
- 不要只基于 1 章记录就提炼正式规则（除非用户明确要求）。
- 不要把 agent 的自我修改当作用户偏好；必须和用户手动修改区分权重。
- 不要使用 StructuredOutput 或任何本环境不存在的工具，主 agent 自己输出 JSON 即可。
- 不要依赖 `/style-distill` 这类 slash command。

## 工作流

### 步骤 0：读取数据

读取：

- `.lingtai/revisions/` 下所有 `第NNN章.jsonl`（忽略 `full/` 子目录中的全量文件，除非需要查看原文）。
- `资料/风格指纹卡.md`（如果已存在）。
- `.lingtai/diff-cache/` 下的旧 `*.json` 作为补充（可选）。

统计：

- 涉及章节数 N。
- user 记录条数、agent 记录条数。
- 全量改写条数。

如果 N < 3：

```
改稿数据不足（当前 N 章）。建议积累至少 3 章改稿记录后再蒸馏。
```

### 步骤 1：给每条记录标注权重

| 情况 | 权重 |
|---|---|
| `source: "user"` 手动修改 | 高：直接代表用户偏好 |
| `source: "agent"` 且用户后续认可、没有回退 | 中：用户认可的方向 |
| `source: "agent"` 但之后被用户改掉 | 低，甚至作为反例：用户最终版本才是偏好 |
| `source: "agent"` 且缺少用户反馈上下文 | 中低：仅作参考 |

当前会话里能看到用户的 prompt 和认可/回退发言时，必须把它写进对应条目的 evidence 里。

### 步骤 2：分维度归类

把每条有效记录分别归到：

**文风层**
- 开头原则（如何进入场景）
- 对白原则（标签、节奏、潜台词）
- 情绪表达（避免情绪总结，偏好动作呈现）
- 句法与节奏（短句、段落长度、断句）
- AI 味红线（删掉哪些模板表达）

**剧情节奏与编排层**
- 章末钩子（落在哪里、不靠作者旁白）
- 冲突类型与升级方式
- 场景-续篇比例 / 情绪消化
- 爽点密度与兑现节奏
- 信息释放边界

### 步骤 3：主 agent 直接输出 JSON

参考以下 schema 输出候选规则。只输出 JSON 对象，放在 Markdown 代码块中：

```json
{
  "style_patterns": [
    {
      "category": "开头原则|对白原则|情绪表达|句法节奏|其他",
      "rule": "对白标签默认用“他说”，不加情绪形容词",
      "frequency": 4,
      "evidence": ["第001章 user：...", "第003章 user：..."],
      "confidence": "high|medium"
    }
  ],
  "pacing_patterns": [
    {
      "category": "章末钩子|冲突类型|爽点密度|场景续篇|信息释放|其他",
      "rule": "章末落在新决定或新风险，不落作者旁白",
      "frequency": 3,
      "evidence": ["..."],
      "confidence": "high|medium"
    }
  ],
  "forbidden_patterns": [
    {
      "pattern": "他感到[情绪]",
      "frequency": 5,
      "examples": ["他感到一阵绝望"]
    }
  ],
  "examples": [
    {
      "category": "对白|开头|情绪|章末|冲突|其他",
      "before": "agent 版",
      "after": "用户版",
      "why_better": "为什么改得好",
      "pattern": "可复用规则"
    }
  ]
}
```

蒸馏原则：

- 至少 3 章出现、或用户 2 次以上手动改出的同一 pattern 才考虑。
- 相似 pattern 合并为一条。
- 优先产出正面指引；红线是补充。
- `frequency` 按有效证据条数填写，不虚标。

### 步骤 4：格式化候选修正案并请用户拍板

展示：

```markdown
## 蒸馏结果（基于 N 章改稿记录）

### 统计概览
- 分析章节：N 章
- 用户手动修改：X 条
- agent 修订：Y 条
- 高频 pattern：Z 个

### 文风偏好候选
#### 1. [开头原则] ...
- 出现频次：...
- 证据：...
- 建议：写入风格指纹卡“文风偏好”部分

### 剧情节奏与编排偏好候选
#### 1. [章末钩子] ...
- 出现频次：...
- 证据：...
- 建议：写入风格指纹卡“剧情节奏与编排偏好”部分

### 红线候选
...

### 标杆例句候选
...
```

然后询问：

```
以上是蒸馏出的 candidate 修正案。

请选择：
1. 全部采纳 - 更新风格指纹卡
2. 部分采纳 - 告诉我采纳哪些
3. 全部拒绝 - 暂不更新
```

### 步骤 5：更新风格指纹卡

用户批准后，更新 `资料/风格指纹卡.md`。

**全部采纳**：
- 读取当前风格指纹卡；
- 将批准项追加到对应 section；
- 更新计数；
- 追加更新日志。

**部分采纳**：
- 只追加用户指定的项。

**预算检查**（建议上限）：
- 文风偏好：正面指引 ≤ 12 条
- 剧情节奏与编排偏好：正面指引 ≤ 12 条
- 红线：≤ 10 条
- 标杆例句：≤ 8 组

如果某 section 已满，询问用户淘汰哪条旧项。

### 步骤 6：确认完成

回复：

```
✓ 风格指纹卡已更新

本次蒸馏：
- 新增文风偏好：N 条
- 新增剧情节奏编排偏好：N 条
- 新增红线：N 条
- 新增标杆例句：N 条

更新后状态：
- 文风偏好：X/12
- 剧情节奏编排偏好：X/12
- 红线：X/10
- 标杆例句：X/8

下次写作时，agent 会通过 system prompt 自动读取这张卡。
```

## 输出风格

- 规则要具体、可执行，不要“更生动”“更自然”这类空话。
- 每条规则都要有 evidence。
- 红线要给出可复制的模板句，方便 agent 识别。

## 和其他 skill 的关系

- `skill-evolution` 负责显式反馈（用户说“记录一下 / 以后别这样”）和流程规则修正。
- `style-distill` 负责从实际改稿中隐式提炼写作口味。
- `chapter-wrap-sync` 在章节收尾时提醒用户是否要蒸馏。
- `style-audit` / `rewrite-to-style` 最终消费风格指纹卡中的规则。
