# Skill Evolution — 写作 skill 持续进化引擎

## 核心理念

skill 不是静态模板——它应该随着用户的写作习惯不断生长。

本 skill 实现一个 **记录 → 沉淀 → 进化** 的闭环：

```
写作会话（chapter-execution / style-audit / rewrite …）
        ↓ 用户修改了什么？忽略了什么建议？抱怨了什么？
     【记录模式】
        ↓ 积累足够多条记录
     【回顾模式】
        ↓ 发现稳定模式，提炼成规则
     【进化模式】
        ↓ 把规则写进对应 skill 的 SKILL.md 或 references/
     【验证 & 回滚】
```

## 数据存储

所有学习数据存放在项目根目录 `.learnings/` 下：

```
.learnings/
├── feedback-log.md        # 时序反馈记录（追加写入）
├── preferences.md         # 沉淀后的偏好清单
├── evolution-log.md       # 进化操作日志
└── snapshots/             # 进化前的 skill 快照（用于回滚）
    └── {skill名}_{日期}.md
```

首次使用时自动创建上述目录和空文件。

## 模式一：记录（Record）

### 何时触发

在以下场景结束后，**由用户主动触发**或由其他 skill 在结尾提示：

- `chapter-execution` 完成后用户大幅修改了产出
- `style-audit` 给出建议后用户表示不认同
- `rewrite-to-style` 改写后用户回退了部分改动
- `dialogue-diagnostics` 的诊断被用户否决
- 任何 skill 使用后用户说了"不对"、"别这样"、"我更喜欢…"

### 用户输入

用户说出以下任一形式即可：
- "记录一下：我不喜欢 style-audit 老是标记短句为 AI 味"
- "这章我改了很多对话，记一下"
- "进化 记录" + 自由描述

### 步骤

1. **确定来源 skill**：用户提到的 skill 名；如果没说，问一下

2. **提取信号**：从用户描述中提取以下字段：
   - `来源skill`：哪个 skill 的产出引发了反馈
   - `信号类型`：以下之一
     - `reject`（拒绝建议）
     - `modify`（接受但大幅修改）
     - `prefer`（用户主动表达偏好）
     - `complain`（抱怨/不满）
     - `praise`（表扬，也要记）
   - `具体内容`：一句话概括
   - `原文片段`（可选）：引用相关文本
   - `用户原话`：用户的原始表述

3. **追加写入** `.learnings/feedback-log.md`，格式如下：

```markdown
---

### #{序号} | {日期} | {来源skill} | {信号类型}

**内容**：{具体内容}

**用户原话**："{用户原话}"

**原文片段**（如有）：
> {片段}

**初步标签**：#{来源skill} #{信号类型} #{关键词}
```

4. **确认**：向用户确认已记录，显示条目摘要

5. **统计提示**：如果该 skill 的记录已累积 ≥5 条，提示用户：
   > "关于 {skill名} 已经积累了 {N} 条反馈，要不要运行一次「回顾」看看有没有稳定模式？"

## 模式二：回顾（Review）

### 何时触发

- 用户说"回顾一下"、"看看积累了什么"
- 某个 skill 的反馈记录 ≥5 条时建议触发
- 用户说"进化 回顾"

### 步骤

1. **读取** `.learnings/feedback-log.md` 全部内容

2. **读取** `.learnings/preferences.md` 现有偏好（如果有）

3. **分 skill 聚类**：按 `来源skill` 分组，统计每组的信号分布

4. **模式识别**：对每个 skill，寻找以下稳定模式：

   | 模式类型 | 判定标准 | 示例 |
   |---------|---------|------|
   | 一贯拒绝 | 同类 reject ≥3 次 | "用户从不接受把短句标记为 AI 味" |
   | 一贯偏好 | 同类 prefer/praise ≥3 次 | "用户喜欢角色内心独白用碎句" |
   | 反复修改 | 同类 modify ≥3 次 | "用户总是把系统提示语从正式改为吐槽风" |
   | 持续抱怨 | 同类 complain ≥2 次 | "用户反复说对话建议太正经" |

5. **生成回顾报告**，格式：

```markdown
# 回顾报告 — {日期}

## 总览
- 累计记录：{N} 条
- 涉及 skill：{列表}
- 本次新发现模式：{M} 个

## 按 skill 分析

### {skill名}（{条数}条记录）

**信号分布**：reject {n} / modify {n} / prefer {n} / complain {n} / praise {n}

**发现的稳定模式**：

1. 🔴 一贯拒绝：{描述}
   - 证据：#{记录编号}, #{记录编号}, …
   - 建议规则修改：{具体建议}

2. 🟢 一贯偏好：{描述}
   - 证据：#{记录编号}, #{记录编号}, …
   - 建议规则修改：{具体建议}

…

### {下一个 skill}
…

## 尚未成模式的信号
（记录少于阈值的零散反馈，留待下次回顾）
```

6. **更新** `.learnings/preferences.md`：把新发现的稳定模式追加进去

7. **询问用户**：
   > "以上模式是否准确？哪些要纳入进化？哪些还需要再观察？"

## 模式三：进化（Evolve）

### 何时触发

- 回顾后用户批准了某些模式
- 用户直接说"进化 {skill名}"并给出具体规则
- 用户说"把这个偏好写进 skill"

### 前置条件

进化操作 **必须** 同时满足：
1. 有明确的用户批准（不能自动进化）
2. 有 ≥3 条支撑证据（除非用户明确说"就一条也要改"）
3. 修改范围清晰（知道改哪个 skill 的哪个部分）
4. 写入目标不是 shipped preset：随部署发布的内置 preset 目录是只读的，必须先复制为项目级或用户级 skill 再修改

### 步骤

1. **确认进化目标**：
   - 目标 skill：哪个
   - 修改类型：
     - `add-rule`：新增一条规则
     - `modify-rule`：修改现有规则
     - `add-exception`：新增一个例外/排除项
     - `adjust-weight`：调整某类检查的权重或优先级
     - `add-reference`：在 references/ 中补充内容
   - 修改内容：具体文字

2. **创建快照**：
   - 先确认目标 skill 可写。内置 preset 目录只读：目标若是 shipped skill，先复制到项目级 `.dsh/skills/<skill名>/`（或用户级 `~/.dsh/skills/<skill名>/`），后续修改与快照都针对该副本
   - 把目标 skill 的当前 SKILL.md 复制到 `.learnings/snapshots/{skill名}_{日期}.md`
   - 如果改的是 references/ 文件，也做快照

3. **执行修改**：
   - 打开目标 skill 的 SKILL.md（或 references/ 文件）
   - 在合适位置插入修改
   - 修改处标注来源：`<!-- evolved: {日期}, 基于反馈 #{编号列表} -->`

4. **记录进化日志**：追加写入 `.learnings/evolution-log.md`：

```markdown
---

### 进化 #{序号} | {日期}

**目标**：{skill名} / {文件路径}
**类型**：{修改类型}
**内容**：{一句话描述}
**依据**：反馈 #{编号列表}
**快照**：snapshots/{文件名}

**具体修改**：
```diff
- {旧内容}
+ {新内容}
```　
```

5. **向用户确认**：展示修改前后对比，确认生效

## 模式四：回滚（Rollback）

### 何时触发

用户说"回滚 {skill名}"或"撤销上次进化"

### 步骤

1. 查看 `.learnings/evolution-log.md` 找到最近一次对该 skill 的进化记录
2. 从 `.learnings/snapshots/` 找到对应快照
3. 用快照内容恢复目标文件
4. 在 evolution-log.md 追加回滚记录
5. 向用户确认已回滚

## 何时使用本 skill

✅ 用：
- 写完一章后想记录"这次 AI 哪里不对劲"
- 积累了一些反馈，想看看有什么规律
- 想把某个发现的规律正式写进 skill
- 想撤销之前的某次 skill 修改

❌ 不用：
- 只是想审稿 → 用 `style-audit`
- 只是想改稿 → 用 `rewrite-to-style`
- 想从零建一个新 skill → 手动创建项目级 `.dsh/skills/<skill名>/SKILL.md`，或在部署允许时创建用户级 `~/.dsh/skills/<skill名>/SKILL.md`

## 不要做的事

- ❌ 未经用户批准自动修改任何 skill 文件
- ❌ 不直接修改 shipped preset 目录中的 skill 文件（升级会覆盖，且 preset 设计为只读）
- ❌ 基于单条反馈就提议进化（除非用户明确要求）
- ❌ 修改 skill 的核心架构（路由、边界、skill 关系）—— 只改具体规则和参考内容
- ❌ 删除 skill 的任何现有步骤 —— 只增加规则、例外或调整权重

## 和其他 skill 的关系

**上游（产生反馈的 skill）**：
- `chapter-execution`：写完章后如果用户大幅改动，提示记录
- `style-audit`：审稿建议被拒绝时，提示记录
- `rewrite-to-style`：改写被回退时，提示记录
- `dialogue-diagnostics`：对话诊断被否决时，提示记录
- `pacing-audit`：节奏建议不被采纳时，提示记录
- `scene-drive`：冲突设计被修改时，提示记录

**本 skill 是纯服务型**——它不产出正文，不做审稿，只负责：
1. 忠实记录用户反馈
2. 发现反馈中的稳定模式
3. 在用户批准后修改其他 skill 的规则

**触发建议**：其他 skill 可在输出末尾加上一句：
> 💡 如果这次的建议有不符合你习惯的地方，可以说"记录一下"让 skill-evolution 帮你沉淀偏好。
